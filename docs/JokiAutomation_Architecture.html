JokiAutomation – Architektur & Signalwege

Einsteiger-Dokumentation für Techniker · .NET Framework 4.8 WinForms-Anwendung zur Automatisierung von Gottesdienst-/Veranstaltungstechnik (Audio, Video/ATEM, PTZ-Kamera, Infrarot/Raspberry Pi, Timer)

Überblick Program.cs Form1 / CommandInterpreter AudioMix & AudioProfile RasPi (SSH) ATEMControl InfraredControl PositionControl & PTZ EventTimer Tests Gesamter Signalweg

1. Überblick

JokiAutomation ist eine WinForms-Anwendung (.NET Framework 4.8), die als CLI-fähige Single-Instance-Anwendung läuft. Sie kann per Kommandozeile (z. B. durch eine Lichtpult-/Regie-Software) angesteuert werden und steuert dabei reale Hardware:

  • Audio-Mixer über den Raspberry Pi (SSH → natives Binary RasPiAutomation)
  • ATEM Videomischer (Blackmagic SDK, COM-Interop) für Kameraschnitt
  • Infrarot-Fernbedienungen (Beamer, TV, Backup) über den Raspberry Pi
  • PTZ-Kameras entweder über Canon-SDK (COM) oder RasPi-Motorsteuerung
  • EventTimer.exe als externer Prozess für Pausen-/Countdown-Anzeigen

Die Projektmappe besteht aus:

ProjektZweck
JokiAutomationHauptanwendung (WinForms, CLI-Dispatch, Hardwareintegration)
CanonPtzCommonGemeinsame Interfaces/Typen für PTZ-Kamerasteuerung (ICanonPtzController)
CanonRemoteControlKonkrete Canon-PTZ-Implementierungen (Legacy AW-Protokoll und XC-SDK)
EventTimerEigenständige WinForms-Anwendung für Pausen-/Countdown-Anzeige auf einem zweiten Bildschirm
JokiAutomation.TestsNUnit-Testprojekt (hardwarefreie Regressions-/Lifecycle-Tests mit Fakes für RasPi-Ausführung)

2. Einstiegspunkt: Program.cs

Der Prozess startet entweder im GUI-Modus (ohne Argumente) oder im CLI-Modus (mit mindestens einem Kommandozeilenargument). Eine Mutex stellt sicher, dass nur eine Instanz läuft; weitere Aufrufe werden über eine Named Pipe an die laufende Instanz weitergeleitet.

JokiAutomation/Program.cs
static class Program
{
	private static Form1 JA;
	private static SingleInstanceCommandServer _commandServer;
	private static ICommandDispatcher _commandDispatcher;
	private static readonly SemaphoreSlim _commandLock = new SemaphoreSlim(1, 1);
	private static readonly AsyncLocal<string> _activeRequestId = new AsyncLocal<string>();

	[STAThread]
	static void Main(string[] args)
	{
		bool isCliMode = safeArgs.Length >= 1;
		// Single-Instance via benannten Mutex, sonst Weiterleitung per Named Pipe
		if (!mutexAcquired)
		{
			PipeCommandResponse forwardResult = ForwardToPrimaryInstance(safeArgs);
			Environment.ExitCode = forwardResult?.ExitCode ?? CommandExitCodes.PipeConnectFailed;
			return;
		}

		if (isCliMode)
			Environment.ExitCode = CommandInterpreter(safeArgs); // CLI: synchron bis Ergebnis
	}
}

CommandInterpreter(string[] args) erzeugt im CLI-Modus eine versteckte Form1-Instanz (die trotz CLI-Aufruf als WinForms-Form existiert, da die gesamte Hardwarelogik an die Form gebunden ist):

private static int CommandInterpreter(string[] args)
{
	Form1 form = new Form1();
	JA = form;
	_commandDispatcher = CreateDispatcher(form);
	// ... startet Message-Loop / wartet auf Ergebnis des Kommandos
}

Jeder eingehende Befehl durchläuft einen globalen Lock (_commandLock, SemaphoreSlim(1,1)), damit niemals zwei Kommandos gleichzeitig auf die Form/Hardware zugreifen, und wird dann per BeginInvoke auf den UI-Thread der Form disponiert:

private static async Task<int> ExecuteOnUiThreadAsync(Form1 form, string[] safeArgs, string requestId, string source, CancellationToken cancellationToken)
{
	var completion = new TaskCompletionSource<int>(TaskCreationOptions.RunContinuationsAsynchronously);

	form.BeginInvoke(new Action(() =>
	{
		_ = ExecuteDispatchedCommandAsync(form, safeArgs, requestId, source, completion);
	}));

	return await completion.Task.ConfigureAwait(false);
}

private static async Task ExecuteDispatchedCommandAsync(Form1 form, string[] safeArgs, string requestId, string source, TaskCompletionSource<int> completion)
{
	string[] formArgs = new string[safeArgs.Length + 1];
	formArgs[0] = "JokiAutomation.exe";
	Array.Copy(safeArgs, 0, formArgs, 1, safeArgs.Length);

	int exitCode = await form.CommandInterpreterAsync(formArgs).ConfigureAwait(true);
	completion.TrySetResult(exitCode);
}

CLI-Aufruf → Mutex/Single-Instance-Prüfung → _commandLock (seriell) → form.BeginInvoke (UI-Thread) → Form1.CommandInterpreterAsync(args)

3. Zentraler Dispatcher: Form1.CommandInterpreterAsync

Diese Methode (in Form1.cs) ist das Herzstück der Kommandoverarbeitung. Sie enthält einen großen switch (cmd), der pro Kommandonamen (z. B. Band, Predigt, Altar, Pause, BEAMER_*, Ausschaltsequenz …) die passende Hardware-Choreografie auslöst. Audio, PTZ/ATEM-Videoumschaltung und Diashow/PiP werden dabei bewusst parallel angestoßen, damit z. B. der Audio-Fade nicht die Video-Umschaltung blockiert:

JokiAutomation/Form1.cs
public async Task<int> CommandInterpreterAsync(string[] commands)
{
	...
	switch (cmd)
	{
		case "Predigt":
			if (!await QueueAudioProfileByNameAsync("Predigt")) // 1) Audio-Profil NICHT abwarten, nur einreihen
			{
				exitCode = CommandExitCodes.CommandFailed;
				return exitCode;
			}

			// 2) Parallel dazu: Bild/Kamera/ATEM umschalten
			await SwitchATEMInputAsync(ATEMInput.CanonPtzPreacher);
			await DisablePictureInPictureAsync();
			break;

		case "Band":
			if (!await QueueAudioProfileByNameAsync("Band"))
			{
				exitCode = CommandExitCodes.CommandFailed;
				return exitCode;
			}
			await SwitchATEMInputAsync(ATEMInput.Laptop);
			await DisablePictureInPictureAsync();
			break;
		...
		default:
			...
			break;
	}

	// 3) Erst JETZT auf den zuletzt eingereihten Audio-Auftrag warten,
	//    damit CLI-Erfolg erst gemeldet wird, wenn Audio wirklich fertig ist
	await AwaitPendingAudioCompletionAsync();

	exitCode = CommandExitCodes.Success;
	return exitCode;
}

Wichtige Designentscheidung: QueueAudioProfileByNameAsync reiht den Audio-Auftrag nur ein (nicht blockierend), damit PTZ/ATEM parallel starten können. Erst am Ende des Kommandos wartet AwaitPendingAudioCompletionAsync() auf den zuletzt eingereihten Audio-Task, bevor CommandExitCodes.Success zurückgegeben wird. Da pro Aufruf genau ein case durchlaufen wird (mutually exclusive switch, je ein break/return), wird der Single-Slot _pendingAudioCompletionTask innerhalb eines Kommandos nie überschrieben.

4. Audio-Pipeline: Form1.AudioProfile.cs & AudioMix.cs

JokiAutomation/Form1.AudioProfile.cs

ApplyAudioProfileByNameAsync sucht das Profil per Name in der UI-Liste (listBox4) und übergibt den aufgelösten Index an SendAudioProfileAsync:

private async Task<bool> ApplyAudioProfileByNameAsync(
	string profileName, TimeSpan? postSendDelay = null,
	CancellationToken cancellationToken = default, bool waitForCompletion = true)
{
	// Profilname -> Index in listBox4 auflösen ...
	return await SendAudioProfileAsync(profileIndex, "CLI_NAME", profileName, postSendDelay, cancellationToken, waitForCompletion);
}

private async Task<bool> SendAudioProfileAsync(int profileIndex, string source, string requestedName, ...)
{
	int commandID = AudioMix.AM_PROFILE + profileIndex;  // 0x70 + Index
	if (waitForCompletion)
	{
		await _audioMix.ExecuteAudioAsync(commandID, cancellationToken);
		await Task.Delay(effectiveDelay, cancellationToken);
	}
	...
}
JokiAutomation/AudioMix.cs

AudioMix kapselt Profil-Konstanten (AM_PROFILE, AM_FADEUP, …) und reicht den eigentlichen Befehl per SSH an den Raspberry Pi weiter. Es gibt eine Legacy fire-and-forget-Variante (rasPiExecute) und die produktive asynchrone Variante:

internal class AudioMix : IDisposable
{
	private const int AM_EXECUTE = 30;   // Audio Mix command (an RasPiAutomation Binary)
	public const int AM_PROFILE = 0x70; // execute audio profile

	public RasPi _rasPi = new RasPi();

	public async Task ExecuteAudioAsync(int ID, CancellationToken cancellationToken = default)
	{
		await _audioDispatchSemaphore.WaitAsync(cancellationToken); // seriell je Audio-Pipeline
		try
		{
			await _rasPi.RasPiExecuteAsync(AM_EXECUTE, ID, cancellationToken: cancellationToken);
		}
		finally { _audioDispatchSemaphore.Release(); }
	}
}

5. Raspberry-Pi-Anbindung (SSH): RasPi.cs / RasPi.Async.cs SSH.NET

Alle hardwarenahen Kommandos (Audio, Infrarot, PTZ-Motor, Shutdown) laufen letztlich über dieselbe SSH-Schnittstelle zu einem natives Binary RasPiAutomation auf dem Raspberry Pi. Die Ausführung ist über IRasPiCommandExecutor abstrahiert, damit Tests einen Fake einsetzen können (SshNetRasPiCommandExecutor in Produktion, FakeRasPiCommandExecutor in Tests):

JokiAutomation/RasPi.cs
partial class RasPi
{
	private readonly IRasPiCommandExecutor _commandExecutor;

	public RasPi() : this(new SshNetRasPiCommandExecutor()) { }

	internal RasPi(IRasPiCommandExecutor commandExecutor)
	{
		_commandExecutor = commandExecutor ?? throw new ArgumentNullException(nameof(commandExecutor));
	}

	[Obsolete("Legacy fire-and-forget adapter. Use RasPiExecuteAsync for productive code.")]
	public void rasPiExecute(int command, int ID)
	{
		_ = Task.Run(async () => await RasPiExecuteAsync(command, ID, cancellationToken: CancellationToken.None));
	}
}
JokiAutomation/RasPi.Async.cs
/// Führt ein Raspberry-Pi-Kommando per SSH aus und wartet vollständig
/// (connect, execute, exit status, stdout/stderr)
public async Task RasPiExecuteAsync(int command, int id, TimeSpan? timeout = null, CancellationToken cancellationToken = default)
{
	string ipAddress = ResolveRaspberryPiIpAddress();     // aus Network.cfg
	string username = ResolveRaspberryPiUsername();
	string password = ResolveRaspberryPiPassword();

	string remoteCommand =
		"echo '" + escapedPassword + "' | sudo -S /home/pi/JokiAutomation/RasPiAutomation " + command + " " + id;

	RasPiCommandExecutionResult result = await _commandExecutor.ExecuteAsync(
		ipAddress, 22, username, password, remoteCommand, effectiveTimeout, cancellationToken);

	if (result == null || !result.ExitCode.HasValue)
		throw new RasPiCommandFailedException(command, id, "RasPi command returned no exit status.");
}

AudioMix.ExecuteAudioAsync(cmdId) → RasPi.RasPiExecuteAsync(30, id) → IRasPiCommandExecutor.ExecuteAsync(...) → SSH → sudo /home/pi/JokiAutomation/RasPiAutomation 30 <id> auf dem Pi → physische Relais/GPIO/IR-Ansteuerung

Das Kommando 30 steht für Audio (AM_EXECUTE), 50 für allgemeine Sequenzen, Infrarot nutzt eigene IDs aus InfraredControl. Die ID (zweiter Parameter) selektiert innerhalb des Kommandotyps die konkrete Aktion/Position/Profil.

6. Videoumschaltung: ATEMControl.cs COM/SDK

Die Videomischer-Steuerung läuft nicht über den Raspberry Pi, sondern direkt per Blackmagic-ATEM-SDK (COM-Interop, BMDSwitcherAPI) über das lokale Netzwerk zum ATEM-Switcher. Ein Semaphore serialisiert Umschaltvorgänge, damit keine zwei Transitionen gleichzeitig laufen:

JokiAutomation/ATEMControl.cs
internal class ATEMControl : IDisposable
{
	/// Ensures only one ATEM transition runs at a time.
	private readonly SemaphoreSlim _transitionSemaphore = new SemaphoreSlim(1, 1);

	public ATEMControl(string ipAddress = "192.168.178.48", Action<string> persistentLog = null)
	{
		_ipAddress = ipAddress;
		_isConnected = false;
	}

	public bool Connect() { // stellt COM-Verbindung zum Switcher her (IBMDSwitcher) ... }
}

Aufrufer ist Form1.SwitchATEMInputAsync(ATEMInput input), das aus dem Kommando-Switch heraus parallel zum Audio-Auftrag aufgerufen wird (siehe Abschnitt 3) und so den Eingang (Laptop, GoPro, Canon PTZ Main/Preacher …) am Mischer umschaltet.

7. Infrarotsteuerung: InfraredControl.cs

Für Beamer, TV und Backup-Steuerung werden IR-Sequenzen über denselben RasPi-SSH-Kanal gesendet wie Audio – nur mit anderer Kommando-ID (IR_EXECUTE/IR_SEQUENCE):

JokiAutomation/InfraredControl.cs
internal class InfraredControl : IDisposable
{
	public void InitIR(Form1 winForm)
	{
		_rasPi = new RasPi();
		_rasPi.initRasPi(winForm);
	}

	/// Sendet Kommando an Raspberry Pi, um IR-Sequenz auszulösen
	public void ExecuteIR(int ID)
	{
		if (_rasPi == null)
			throw new InvalidOperationException("Infrared control not initialized. Call InitIR() first.");

		_rasPi.rasPiExecute(IR_EXECUTE, ID);
	}
}

Im Hauptswitch wird dies über ExecuteIrSequenceAsync(InfraredControl.IR_BEAMER_TOGGLE, "BEAMER_LiveStream", timeout) aufgerufen, z. B. in den case "BEAMER_*"-Zweigen von CommandInterpreterAsync.

8. Kamerapositionierung: PositionControl.cs, CanonPtzCommon, CanonRemoteControl COMMotor/RasPi

PositionControl unterstützt zwei Modi für die Kamerapositionierung, abhängig von Konfiguration (isPtzMode): entweder Motorsteuerung über den Raspberry Pi (Analogkamera auf Schlitten/Pan-Tilt-Kopf) oder eine echte Canon-PTZ-Kamera über ICanonPtzController. Die IR-/Beamer-Steuerung über RasPi bleibt in jedem Fall aktiv:

JokiAutomation/PositionControl.cs
class PositionControl : IDisposable
{
	/// - Raspberry Pi: ALWAYS active (IR sequences, Audio, Beamer control)
	/// - Camera positioning: Either RasPi motor control OR Canon PTZ (depending on PTZ_CAM setting)
	public void initPC(Form1 winForm, bool isPtzMode = false, ICanonPtzController canonPtzController = null)
	{
		_isPtzMode = isPtzMode;
		_canonPtzController = canonPtzController;
		_rasPi.initRasPi(winForm); // RasPi wird IMMER initialisiert (für IR-Steuerung)
	}
}

9. Pausen-/Timeranzeige: EventTimer.cs externer Prozess

Für Pausenbildschirme und Countdown wird nicht JokiAutomation selbst verwendet, sondern das separate Projekt EventTimer als eigenständige EventTimer.exe, die mit Kommandozeilenargumenten gestartet wird:

JokiAutomation/EventTimer.cs
internal class EventTimer : IDisposable
{
	private const string EXECUTABLE_NAME = "EventTimer.exe";

	/// Startet EventTimer.exe im Pausenmodus mit zwei Anzeigetexten
	public EventTimerStartResult sendPause(string text1, string text2, string requestId = null, string source = "UNKNOWN")

		string arguments = $"Pause {EscapeArgument(text1)} {EscapeArgument(text2)}";

Wird aus CommandInterpreterAsync im case "Pause" bzw. case "Timer" über ExecutePauseCommandAsync/ExecuteTimerCommandAsync aufgerufen (Process.Start auf EventTimer.exe).

10. Testprojekt: JokiAutomation.Tests

Hardwarefreie Tests ersetzen die SSH-Schicht durch FakeRasPiCommandExecutor (implementiert IRasPiCommandExecutor), sodass Regressions- und Lifecycle-Tests ohne echten Raspberry Pi laufen können. Wichtige Fixtures:

  • Fakes/FakeRasPiCommandExecutor.cs – zeichnet Kommandos auf, erlaubt deterministische Start-/Completion-Gates.
  • Unit/RasPiExecuteAsyncTests.cs – prüft Fehler-/Exit-Code-Handling von RasPiExecuteAsync.
  • JokiAutomation.LifecycleTests.cs & Regression-Tests – prüfen das Zusammenspiel von CLI-Dispatch, CommandInterpreterAsync und Audio-Lebensdauer (z. B. dass CLI-Erfolg erst nach Abschluss des Audio-Auftrags gemeldet wird).

11. Gesamter Signalweg am Beispiel Predigt

Zusammenfassung des kompletten Wegs eines CLI-Kommandos von der Konsole bis zur Hardware:

1. Konsole: JokiAutomation.exe Predigt
2. Program.Main → Mutex-Prüfung → CommandInterpreter(args)
3. _commandLock (Serialisierung) → ExecuteOnUiThreadAsync → form.BeginInvoke
4. Form1.CommandInterpreterAsync: switch(cmd) → case "Predigt"
5a. QueueAudioProfileByNameAsync("Predigt") → SendAudioProfileAsync → AudioMix.ExecuteAudioAsync → RasPi.RasPiExecuteAsync(30, id) → SSH → RasPiAutomation auf dem Pi
5b. parallel dazu: SwitchATEMInputAsync(CanonPtzPreacher) → ATEMControl (COM) → ATEM-Switcher im Netzwerk
6. AwaitPendingAudioCompletionAsync() wartet auf Abschluss von Schritt 5a
7. Rückgabe CommandExitCodes.Success → completion.TrySetResult → CLI-Exitcode an aufrufenden Prozess

Dieses Muster (Audio asynchron einreihen, Video/PTZ parallel ausführen, am Ende auf Audio-Abschluss warten) gilt analog für alle anderen Kommandos im Switch (Band, Text, GoPro, Altar, Gebet, LesungMulti, BandMulti).
